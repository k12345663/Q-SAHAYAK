# QSahayak — Continuation Guide

Handoff doc for picking this project up in a fresh Claude session with zero prior context. Paste this file's path (or its contents) at the start of the new conversation and say what you want worked on — the "Next: refine scheme recommendation" section at the bottom is the current priority.

## 1. What this is

An Intelligent Government Scheme Recommendation System (final-year project). A citizen fills a short profile form, gets a ranked list of government welfare schemes they likely qualify for, with plain-language reasons, in English/Hindi/Marathi. Ranking is a genuine hybrid classical + quantum pipeline (QAOA on Qiskit), not just a label.

Two run targets:

```bash
# Frontend (React + Vite + TypeScript + Tailwind v4)
cd govt-scheme-recommender && npm run dev          # http://localhost:5173

# Backend (FastAPI + Qiskit QAOA)
cd govt-scheme-recommender/backend
source .venv/bin/activate
uvicorn main:app --reload --port 8000               # http://localhost:8000
```

The frontend works standalone (falls back to classical ranking with an honest "quantum backend unavailable" banner if the backend isn't running) — but the backend is what makes the quantum claim real, so start both.

## 2. What's real vs simulated — read this before claiming anything to a professor/evaluator

| Piece | Status | Where |
|---|---|---|
| Classical hard-filter + weighted eligibility scoring | **Real**, runs in-browser | `src/lib/matcher.ts` |
| QAOA quantum-classical hybrid optimizer | **Real** — actual QAOA circuits solving a genuine QUBO (benefit maximization − redundancy conflicts − cardinality penalty) on Qiskit's `StatevectorSampler` | `backend/main.py` |
| 555-scheme catalog (names/ministry/level/state/category) | **Real data**, extracted directly from `Government_Schemes_Full_Document.docx` | `src/data/schemes_raw.json`, `backend/extract_schemes.py` |
| Catalog per-scheme eligibility | **NOT real per-scheme** — the source document itself only gives one generic "typical" eligibility paragraph *per category* (16 total), reused across all schemes in that category. We score against that as a soft signal, never claim a scheme-specific verdict. **This is the #1 thing to refine — see §5.** | `src/data/categoryRules.ts`, `src/lib/catalogMatcher.ts` |
| Document (VLM) verification | **Simulated** — plausible fake OCR output, not a real vision model | `src/lib/documentVerification.ts` |
| Chat assistant | **Simulated** — keyword-matching over structured scheme data, not a real LLM call | `src/lib/chatAssistant.ts` |
| Multilingual UI strings | Real, hand-translated (EN/HI/MR) | `src/i18n/strings.ts` |

Why the QAOA claim is defensible despite being "just a simulator": no real QPU would help at this problem size — this matches standard academic practice and was a deliberate scope decision, not a shortcut. It's stated honestly everywhere in code comments and UI copy.

## 3. Architecture map

```
User fills form (EligibilityForm.tsx)
        ↓
UserProfile { name, age, gender, income, occupation, state, category, disability, land, BPL }
        ↓
   ┌────────────────────────────┬─────────────────────────────┐
   │                            │                              │
matcher.ts                catalogMatcher.ts                    │
(14 curated schemes,      (555 catalog schemes,                │
 hard filter + score)      soft category-level relevance)      │
   │                            │                              │
   └──────────┬─────────────────┘                              │
              ↓                                                │
   merged into QuantumCandidate[] in Results.tsx                │
              ↓                                                │
   quantumRanker.ts → POST /api/rank → backend/main.py (QAOA)  │
              ↓                                                │
   "Quantum-optimized pick" badges + reordering                │
              ↓                                                │
   Results.tsx renders: curated SchemeCards, catalog top        │
   matches (CatalogRow), full CatalogBrowser modal, ChatWidget │
```

Key files:

- `src/types/index.ts` — all shared types (`UserProfile`, `Scheme`, `ScoredScheme`, `CatalogScheme`, `ScoredCatalogScheme`, `CategoryRule`)
- `src/data/schemes.ts` — the 14 hand-curated, fully-detailed schemes (benefits, required docs, application steps, official URLs)
- `src/data/schemes_raw.json` — the 555-scheme catalog (generated by `backend/extract_schemes.py`, don't hand-edit; re-run the script if the source docx changes)
- `src/data/categoryRules.ts` — 16 category-level soft scoring rules, one per catalog category
- `src/data/sectorCategoryMap.ts` — maps the 14 curated schemes' `sector` enum onto the same 16 category names, so quantum conflict-grouping works across both tiers
- `src/data/conflicts.ts` — small supplementary hardcoded conflict list (currently just `[['apy', 'pmsym']]`); dynamic category-based conflicts in `quantumRanker.ts` now do most of the work
- `src/lib/matcher.ts` — hard filter + weighted score for the 14 curated schemes
- `src/lib/catalogMatcher.ts` — soft relevance score for the 555 catalog schemes; state-domicile mismatch is the one hard filter
- `src/lib/quantumRanker.ts` — builds the candidate list + dynamic conflicts, calls the backend, times out gracefully
- `backend/main.py` — FastAPI service; `/api/rank` builds a QUBO and solves it with `qiskit_algorithms.QAOA`
- `src/components/Results.tsx` — orchestrates everything above into the results screen
- `src/components/CatalogBrowser.tsx` — searchable/filterable modal over all 555 schemes (also exports `CatalogRow`, reused for the compact "top matches" list)

## 4. Known gotchas (don't re-debug these)

- **`qiskit-aer`'s `SamplerV2` is broken with `qiskit-algorithms`' QAOA circuits** on this stack (`AerError: unknown instruction: QAOA`) — this is why `backend/main.py` uses `qiskit.primitives.StatevectorSampler` instead of Aer directly. Still genuine QAOA, just not literally "Aer."
- **QAOA solve time is O(2ⁿ) in qubit count.** Benchmarked: 6 qubits ≈1.5s, 7 qubits ≈1.1–2s (after tuning), 9 qubits ≈62s, 14 qubits >120s (killed). Backend caps candidates at `MAX_CANDIDATES = 7` in `main.py` — don't raise this without re-benchmarking, or add async job handling if you need more.
- **Never export a hook and a component from the same file** — it breaks Vite Fast Refresh and causes a real "must be used within Provider" crash after a few HMR cycles (happened with the old `LangContext.tsx`). It's now split into `langContextBase.ts` (context object) / `LangContext.tsx` (provider component only) / `useLang.ts` (hook only). Keep that split for any future context.
- If dev-server console errors look like stale/duplicated module state after several edits, do a full `preview_stop` + `preview_start` (not just a page reload) — Vite's HMR module graph can get corrupted mid-session.
- The Python venv is at `backend/.venv` (Python 3.14, works fine — qiskit/qiskit-aer had prebuilt wheels despite being bleeding-edge). `backend/requirements.txt` is pinned to known-working versions.

## 5. Next: refine scheme recommendation (the actual ask)

Ordered by value-per-effort. Pick up from the top.

### 5.1 Parse scheme names for stronger per-scheme signals (do this first — no new data needed)

Right now all 92 "Student / Education & Scholarships" schemes share one eligibility template, even though scheme *names* already encode real signals: "Pre-Matric Scholarship **for SC Students**", "AICTE Pragati Scholarship **for Girls**", "Top Class Education Scheme **for Students with Disabilities**", "**Maharashtra** EBC Freeship Scheme". Write a name-parser (regex/keyword based, no ML needed) that extracts:

- caste/community reservation (`SC|ST|OBC|Minority|EWS` in the name → boost that specific category, not just "reservation where applicable")
- gender (`Girls|Women|Mahila|Kanya|Beti` → female-targeted)
- disability (`Disabled|Divyang|Viklang` → `requiresDisability`)
- age cohort words (`Senior Citizen`, `Bal`/child terms)

Apply this as a *per-scheme override* on top of the category-level `CategoryRule` in `catalogMatcher.ts`, before the additive scoring. This alone should sharply improve precision for the ~200+ schemes whose names are self-descriptive, at low effort.

### 5.2 Deduplicate curated vs. catalog tiers

The 14 curated schemes (e.g. `pm-kisan`) also exist as separate, differently-scored entries in the 555-catalog (e.g. "PM-KISAN (PM Kisan Samman Nidhi)"), so a user can see the same real-world scheme twice with two different scores and no cross-reference. Build a name-similarity check (normalize + token overlap, or a small alias table) in `Results.tsx` or a new `src/lib/dedupe.ts` that suppresses a catalog entry when a curated scheme clearly represents the same real scheme. Decide: suppress entirely, or merge into one card that shows the curated tier's rich detail with a "also in catalog" note.

### 5.3 Expand the curated (fully-detailed) tier past 14

The 14 curated schemes get real hard-filter eligibility, benefits, required docs, and application steps. The other 541 don't have that detail because it isn't in the source docx. Pick the ~30–50 highest-traffic/most-searched schemes (scholarships, PMAY, Ayushman Bharat variants, MGNREGA, PMKVY, etc.) and hand-curate them the same way `src/data/schemes.ts` does today — same `Scheme` type, same rigor. This is manual research work (verify against myscheme.gov.in), not something to fabricate.

### 5.4 Collect richer profile signals where they'd actually change the answer

The document's category rules reference things the current `UserProfile` (`src/types/index.ts`) doesn't capture: highest education level (many scholarships gate on "8th pass" vs "graduate"), whether the applicant already has an LPG connection/toilet/electricity (utility schemes), vehicle ownership (EV incentive schemes), number/age of children (women & child schemes). Only add a field if you also update the scoring in `catalogMatcher.ts` (and `matcher.ts` if it affects the curated 14) — don't collect data nothing uses.

### 5.5 Principled weight tuning

`catalogMatcher.ts`'s scoring is currently hand-picked additive points (+20 / -15 / etc.), not validated against anything. Build a small labeled test set — 15–20 synthetic profiles with a manually-verified "should rank highly" scheme list each — and tune the weights against it before/after each change in §5.1–5.4, so refinements are measured, not vibes-based.

### 5.6 (Optional, bigger scope) Real per-scheme eligibility via research/LLM lookup

The original project pitch envisioned RAG over real scheme pages. If you want to go there: for each catalog scheme, look up its actual page on myscheme.gov.in (or the ministry's page) and extract structured eligibility (age/income/occupation) into the same shape as `SchemeEligibility` in `src/types/index.ts`, with a `sourceUrl` and `lastVerified` date so staleness is visible. This is real research effort across potentially hundreds of schemes — scope it explicitly (e.g. "top 100 by category-match frequency") rather than attempting all 555 at once. Don't let an LLM invent eligibility numbers it hasn't actually looked up; that would reintroduce the exact fabrication problem the current soft-scoring design was built to avoid.

### Not in scope for "scheme recommendation" — separate tracks if pursued

- Real VLM document verification (`src/lib/documentVerification.ts` is simulated) — a vision-model integration project on its own.
- Real LLM-backed chat (`src/lib/chatAssistant.ts` is rule-based) — needs a backend proxy endpoint (never call an LLM API with a key from the browser), and a cost/budget decision.
- WhatsApp/SMS bot, admin analytics dashboard, blockchain audit trail — from the original pitch, not built, not requested since.
